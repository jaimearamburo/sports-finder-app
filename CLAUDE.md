# Sports Booking App — Project Memory

Read `MVP_TASK_BREAKDOWN.md` in this same repo for the full numbered ticket list, time estimates, and dependency order. This file covers everything else: project context, decisions made, current state, and hard-won gotchas.

## Project overview

A sports/activity booking platform for discovering and booking tennis courts, padel courts, campsites, and fitness classes. Full-stack Next.js/TypeScript application, developed under an accelerated, scope-disciplined timeline — every scope decision in this project prioritizes the simpler, shippable option over the more "complete" one unless explicitly noted otherwise.

## Tech stack

Next.js (App Router, latest) + TypeScript. Tailwind CSS + Shadcn UI (Shadcn is built on Radix/Base UI primitives + Tailwind styling — not a competing library; this project's shadcn install uses the `base-vega` style on `@base-ui/react`, not classic Radix). PostgreSQL on Supabase. Prisma ORM (v7 — see gotchas section, this version introduced major breaking changes vs. what most tutorials/training data will assume). Auth.js (NextAuth) — self-implemented rather than a third-party auth SaaS (e.g. Clerk), to keep full control over the auth flow and avoid an external vendor dependency. Stripe (test mode; Payment Element on the site's own checkout page - see "Payments" below). Deployed on Vercel, connected via Vercel's Supabase Marketplace integration (env vars auto-synced, not manually managed).

Package manager is **pnpm**, not npm — this matters, pnpm has different install/build-script behavior (see gotchas).

## Data model (current)

- **User** — role enum (`admin` / `venue_owner` / `user`). A venue_owner can own multiple venues from one account (`Venue.ownerId` is just a foreign key on Venue, not a special account type). Multi-manager-per-venue (many-to-many staff) was considered and explicitly deferred — not built.
- **City** — platform-curated reference data, same pattern as Tag/Activity (venue managers pick from this list rather than typing a city name freely). Has `name`, `region`, `timezone`. `Venue.cityId` is a foreign key into this, not a free-text string.
- **Venue** — belongs to one owner (User) and one City. Has `address` as plain text (no lat/long — real distance-based search is explicitly future work). `bookingWindowDays` (default 30) is the rolling public booking window; `holdDurationMinutes` (default 5) is the default cart-lock duration, inherited by its Listings unless overridden.
- **Activity** — a platform-wide category (Tennis, Padel, Camping, Gym Class, Tennis Class, etc.) — NOT scoped to a venue. Admin-managed conceptually (no admin UI built; managed via the seed script only, by design, for MVP). Has a `bookingMechanic` enum: `time_range` (pick a start time + duration — courts), `date_range` (pick start/end date — camping), or `fixed_session` (book into one scheduled occurrence — classes).
- **Listing** (renamed from the original "Resource") — the actual bookable thing at a specific venue ("Court 1," "Campsite A," "Monday 6pm HIIT"). Belongs to one Venue + one Activity. `capacity` is nullable (`null` = unlimited, e.g. a free group run). Has availability-rule fields that differ by its Activity's `bookingMechanic` (operating hours/duration/increment for `time_range`; min/max days for `date_range`; recurrence day/time/duration for `fixed_session`). `archivedAt` (nullable) retires a listing from browse/booking without deleting it — deleting would cascade and destroy booking history, which `Booking.listing`'s `onDelete: Restrict` explicitly prevents; archiving is the only supported way to retire a listing with any booking history.
- **Booking** — belongs to one Listing, optionally one User (null = guest booking, with `guestName`/`guestEmail`/`guestPhone` used instead — schema supports this, but the booking flow built so far requires login; see Auth model). Always stores its own `startsAt`/`endsAt` directly. `quantity` (default 1) is how many capacity units one booking claims, letting a group claim several spots in one purchase without the capacity check under/over-counting. `attendeeName`/`attendeeEmail`/`attendeePhone` (mandatory except phone) capture who the booking is actually for, collected at checkout regardless of account status — distinct from the guest fields above, since a logged-in user can still book on behalf of someone else. `orderId` groups every row created from one checkout attempt (a multi-day pass is several rows) under one user-facing reference — see "Booking hold + confirm flow" below.
- **Tag** + **ActivityTag** (join table) — many-to-many quick-filter tags for the browse UI. An Activity can carry multiple tags — "Tennis Class" is tagged both "Tennis" and "Classes." `Tag` also carries `emoji`, `color`, `displayOrder` for the browse chip row.
- **AvailabilityOverride** — venue-wide or listing-specific exceptions to the normal booking window: `block` (unavailable) or `open` (available/extends past the window), either a one-off date(s) or a recurring weekly rule (`daysOfWeek`). No admin UI exists to create these yet — currently seed-script-managed only (two sample rows: a `block` on a court, an `open` on a class). See "Booking availability design" below for the resolution rules, which took real iteration to get right.
- **BookingHold** — a temporary cart-lock so two people can't finish checkout on the same slot at once. **Fully implemented** — see "Booking hold + confirm flow" below. `quantity` mirrors `Booking.quantity`, so a group's hold blocks the right amount of capacity for everyone else. `orderId` (see `Booking.orderId` above) is generated once per checkout attempt and shared by every hold row it creates.

**There is deliberately no "Slot" table anywhere in this schema.** Pre-generating discrete bookable time-slot rows doesn't scale once booking duration is variable. Instead: `Booking.startsAt`/`endsAt` are always stored directly against the Listing, and conflict prevention is an **application-level check inside a transaction** — sum the `quantity` of existing non-cancelled Bookings and active BookingHolds on that Listing whose time range overlaps the requested range, reject if that sum plus the new request would exceed `Listing.capacity` (skipped entirely when capacity is `null`). This check is now hardened against real concurrent requests via a `SELECT ... FOR UPDATE` row lock on the `Listing` row — see "Booking hold + checkout flow" below for why that lock is necessary and how it was verified.

Naming convention: Prisma model/field names are camelCase (idiomatic TS), mapped to snake_case actual Postgres tables/columns via `@map`/`@@map`.

## Auth model

Auth.js is fully implemented: Credentials (email/password via bcrypt) + Google OAuth providers, JWT sessions (required since Credentials can't use database sessions), `auth()`/`signIn()`/`signOut()` exported from `auth.ts`. Real login/signup pages with server actions (`app/login/actions.ts`, `app/signup/actions.ts`).

Three roles: `admin` (full access), `venue_owner` (manage only venues where `Venue.ownerId` matches their own user id — not exclusive, can also browse/book like a normal user elsewhere), `user` (browse/book/manage own bookings).

**Guest checkout**: the schema supports it (nullable `Booking.userId` + guest contact fields), but the booking flow built so far (`createBookingHold`/`startHoldPayment`/`confirmHoldPayment`, see "Booking hold + confirm flow" below) **requires login** — a deliberate scope decision for the first working version, not a limitation of the data model. Revisit as its own ticket if guest checkout turns out to matter before launch.

**Header account menu** (`components/layout/account-menu.tsx`, links from `lib/account-nav.ts`): signed in, the header shows an account button - initials, name and a role badge ("Venue owner", "Admin"; none for regular users, `getRoleBadge`) from `md` up, initials only on phones - so it's always visible which account is in use. It opens a menu with name, email, role, the account links and Log out. Links are permission-based (`getAccountLinks`): anyone with `dashboard:access` gets "Dashboard" → `/dashboard` and "My Bookings" → `/account` (owners book too); everyone else "My Account" → `/account`. Signed-out visitors get Log in / Sign up (links on desktop, a menu on phones). `/account` has a real side-nav scaffold (`app/account/layout.tsx`, using the shared section nav).

**My Bookings** (`app/account/page.tsx`) — every order the signed-in user has ever made, as a table: reference, listing/venue, date, and an "Upcoming"/"Past" status badge. `getUserBookingOrders` (`lib/bookings.ts`) groups individual `Booking` rows back into one entry per `orderId` (the same grouping the confirmation page does for a single order, just across all of them) — a multi-day pass is one row, not several. Status is decided by the order's *latest* slot, not its earliest: a pass with its first day gone but its last day still ahead stays "Upcoming" until every slot in it has elapsed. Orders are sorted upcoming-soonest-first, then past-most-recent-first. The reference number (`getBookingReference`, `lib/booking-reference.ts` — the same 8-character display code the confirmation page shows) is the only clickable thing in a row; clicking it opens a `Dialog` (one shared instance, driven by which `orderId` is "open," not one per row) with the full per-slot breakdown — there's no separate detail page to navigate to, since the table already holds everything. The account area and the venue dashboard share one layout: `SectionPageShell` (`components/layout/section-page-shell.tsx`, the same sidebar-on-desktop / pill-row-on-phones swap as `BrowsePageShell`) and `SectionSidebarNav`/`SectionMobileNav` (`components/layout/section-nav.tsx`), each area passing its own links - one design, not drifting copies.

**Demo logins** (`lib/demo-login.ts`, provider `demo` in `auth.ts`, buttons `app/login/demo-login-buttons.tsx`): a "Try the demo" box on the login page with "Log in as regular user" and "Log in as venue owner". No password is involved: the buttons send only `account=user|owner`, and the server signs in the account named by `DEMO_USER_EMAIL` / `DEMO_OWNER_EMAIL`. Off unless `DEMO_LOGIN_ENABLED=true` (box hidden, provider refuses). **Admin accounts are always refused**, so a misconfigured email can't make admin public. Demo visitors can change anything those accounts can (an explicit decision: a fully working demo). Dev uses Emma Collins (`emma.owner@example.com`) and "Demo User Account" (`demo-user@example.com`, no password, so only reachable through the button); production needs the env vars in Vercel and the accounts in its database. Tested in `e2e/demo-login.spec.ts` and `lib/demo-login.test.ts`.

**Authorization pattern** (established convention, use for all future protected pages and actions). Three layers, as in Next.js's own authentication guide (`node_modules/next/dist/docs/01-app/02-guides/authentication.md`):
1. **Route level (`proxy.ts`), optimistic only:** reads `lib/authz/route-access.ts` (route → required permission, segment-aware prefix match). Signed out → `/login?callbackUrl=…`; signed in without the permission → home. Convenience, not protection: it only sees the JWT cookie, and Server Actions don't go through pages.
2. **Page level:** every protected page's first line is `requirePermission(permission)` (`lib/auth-guards.ts`), which renders not-found (not a 403, so the area doesn't confirm it exists) when not allowed. Never rely on a layout for this - layouts don't re-render on client navigation. Verified by disabling the proxy rule: a regular user still gets a 404 on `/dashboard`.
3. **Data level (authoritative):** DAL functions are wrapped in `withAuth` (any signed-in user, e.g. booking) or `withPermission(permission, fn)`; there's no code path to the `session` parameter except through the wrapper. Server Actions stay thin (`app/.../actions.ts`, `"use server"`) and delegate to a `server-only` DAL module (e.g. `lib/bookings.ts`), per `data-security.md` in the same docs.

**Check permissions, never roles.** `lib/authz/permissions.ts` is the single role → permission map (`can(user, permission)`); its `Record<UserRole, …>` makes a new database role a compile error until it's given permissions. Roles live on `User.role` (in the JWT); what they grant lives in code. **Ownership is a separate check** (`lib/authz/policies.ts`: `canManageVenue`, `canManageListing`, and `manageableVenuesWhere` to scope list queries): holding `venues:manage` doesn't mean owning *this* venue, so record-level actions load the row and ask the policy (admins pass via `venues:manage-all`, not a role check). An owner requesting another owner's record should get "not found". The same split Laravel calls Gates vs Policies. Unit tests: `pnpm test` (Vitest, `lib/authz/*.test.ts`).

## Booking availability design

`lib/availability.ts`'s `getBookableDates(listing)` is the single source of truth for which calendar dates a listing can be booked on, used by both the (future) picker UI and the server-side re-validation. The rules, several of which were deliberately chosen over a more "complete"-seeming alternative:

- **Base window**: today through `Venue.bookingWindowDays` (30 by default), every day for `time_range`/`date_range` (both assumed open daily), or only the matching weekday for `fixed_session`.
- **Override resolution**: a `listing`-scoped override wins over a `venue`-scoped one on the same date. Inside the normal window, a date is available by default unless a `block` says otherwise; beyond the window, a date is unavailable by default unless an `open` says otherwise.
- **No `endDate` at all means the override applies on its `startDate` only** — a single day — regardless of whether `daysOfWeek` is set. This was a deliberate simplification over the originally-documented "recurring + no endDate = indefinite": true indefinite recurrence would need its own cutoff anyway (nothing can really be bookable forever), and since the hard cap below already makes "indefinite" and "ends 90+ days out" functionally identical, supporting true indefinite buys no real capability — only ambiguity (same field meaning two different things depending on another field) and a query that could never prune old rows. If this needs revisiting, do it as a UI default (an "open indefinitely" checkbox that just fills in `endDate = startDate + 90 days`), not a schema/logic change.
- **`MAX_OPEN_EXTENSION_DAYS = 90`** — a hard ceiling on how far an `open` override can push bookability, regardless of its own `endDate`. Without this, one override with a far-future `endDate` could make a listing bookable for a year+ straight.
- **An `open` override can never add a date outside a `fixed_session` listing's own weekday** — the pattern check runs before any override is consulted. A genuinely different one-off occurrence (e.g. a surprise Wednesday class on a normally-Monday-only listing) needs its own `Listing` row, not an override. No admin UI exists yet to create overrides at all, so nothing currently enforces this on the way in — worth a real validation rule once one does.
- Past overrides are excluded from the query itself (not just filtered out by the date logic), since they can never apply to any date the function actually checks.

`isRequestedSlotValid(listing, startsAt, endsAt, bookableDates)` re-derives whether a submitted slot is actually legal per-mechanic (operating hours/increment/duration bounds for `time_range`, day-count bounds for `date_range`, exact occurrence match for `fixed_session`) — the server action calls this itself rather than trusting client input, since a picker UI enforcing the same rules doesn't stop a direct POST request from sending anything.

## Booking hold + confirm flow

A booking is a two-step reserve-then-confirm flow, not a single direct write, so two people can never both finish checking out on the same slot:

1. **Slot selection** (`SlotPicker`) is pure client state — no server call, no hold yet. A multi-day pass picker disables every unpicked day once the maximum is picked ("…, the most allowed. Unpick one to change.") - react-day-picker's own `max` handling replaced the whole selection with the extra day; one-day passes keep that swap.
2. **Clicking "Book Now"** while signed out shows "You must log in to make a booking." with "log in" linking to `/login?callbackUrl=/listings/<id>`, back to the listing after logging in (`withAuth` marks the refusal `signedOut: true`, so callers don't match on the message). Signed in, it calls `createBookingHold` (`lib/bookings.ts`), the actual moment a hold is created. `slots` is always an array (even for the common single-slot case) because a non-accommodation `date_range` "pass" (several individually-picked days, e.g. the 19th/23rd/30th) produces multiple one-day spans, not one — all slots in a request succeed or fail together, since a pass missing one of its picked days isn't a valid purchase. Every row created from one checkout attempt shares one `orderId` (a `crypto.randomUUID()`, generated once in application code, not a column default), so the user-facing URL and UI only ever expose that one reference, never the individual row ids underneath. On success, redirects to `app/listings/[id]/checkout/[orderId]/page.tsx` with the hold(s) already active.
3. **The checkout page** (`CheckoutForm`, a Client Component) shows a live countdown to `expiresAt` (numbers in red), an attendee-details form ("Booking for myself" pulls `User.name`/`email`; "Booking for someone else" clears the form and focuses the first field), a mandatory "I agree to \<venue\>'s Terms and Conditions" checkbox (the Terms link opens a `Dialog` with short demo copy - sample venue, nothing reserved, test payments - rather than navigating to the site-wide `/terms` page; booking terms are meant to be per-venue, editable by venue managers eventually), and the Stripe Payment Element (see "Payments" below) with a test-card hint: a blue info box ("Test mode, no real charges", the 4242 number in bold, a "Copy card number" button whose text never changes; a small "Copied" bubble appears above it and fades after 2 seconds, so nothing shifts - `TestCardHint`). Attendee inputs and Stripe's card fields are white (`bg-card`; the Stripe appearance's `.Input` rule) so they stand out from the grey page. Blue, not amber, since amber is reserved for hold warnings. The card fields can't be filled in for the visitor: they live in Stripe's iframe, out of the page's reach by design, hence copy rather than autofill. The countdown hitting zero client-side is purely a UX signal; expiry is always re-checked server-side on submit. "Back to listing" is plain navigation only - it does **not** release the hold (that was built, then removed: it was silently clearing the hold with no warning, which made the active-hold banner look inconsistent rather than like cause and effect). The only way to cancel early is the listing page's own active-hold banner, below. "Back to listing" uses `router.back()`, not `router.push()`, and that distinction matters twice over: `push()` would add a duplicate history entry for a URL already in the stack, which is what caused a real reported bug (go back to the listing, then click "Go back" there, and it only popped that duplicate entry, landing back on checkout instead of browse); and any back/forward navigation restores the page from Next's in-memory history cache rather than re-fetching (Next does this by design; `staleTimes` can't change it), which showed a stale pre-hold render with no banner. `RefreshOnHistoryNavigation` (`components/layout/`, mounted in the root layout) fixes this for the browser's own back/forward buttons and `router.back()` alike: on a history navigation that lands on a `/listings/*` page (detail or checkout) it calls `router.refresh()`, deferred one tick so Next finishes restoring first. Scoped to listing pages on purpose - refreshing every page on back would re-run the heavy browse query.
4. **Paying** authorizes the card, then converts the hold(s) into `Booking` row(s) and captures the money - see "Payments" below. `amountPaid` is computed the same way the checkout page's own total is; every row shares the `orderId`.
5. **Redirects to `app/bookings/confirmation/[orderId]/page.tsx`** — a minimal confirmation page, not the full "My Bookings" dashboard (that's its own later ticket). Shows a "Booking reference" — the first 8 characters of `orderId`, uppercased, display-only; the full `orderId` (already in this page's own URL) stays the real lookup key everywhere else.

**One active hold per user, platform-wide.** `createBookingHold` rejects a new hold if the user already has one anywhere (any listing), until it's finalized, explicitly cancelled, or naturally expires. This is deliberately simpler than trying to reliably detect "the user navigated away" (a real mechanism — releasing on component unmount plus a `pagehide`/`sendBeacon` call to a REST route for actual tab-close — was built and then removed once this rule made it actively counterproductive: it would have silently undone the lock the moment someone glanced at another page). Enforced with the same lock-then-check shape as the per-listing capacity check, just scoped to the `User` row instead of the `Listing` row, closing the same two-concurrent-requests race. Surfaced proactively, not just as a rejected "Book Now" click: `app/listings/[id]/page.tsx` checks for the user's own active hold on every listing page (not just the one it's for) and, if found, renders `ActiveHoldBanner` — the listing it's for, a "Resume checkout" link, and a "Cancel" button — with the rest of the page blurred and inert underneath (`pointer-events-none blur-sm`) until it's resolved. The banner scrolls the page to the top when it appears (the listing usually comes back from checkout at the bottom, where Book Now is), and its cancel button reads "Cancel booking". Tested in `e2e/booking-hold.spec.ts`.

**Concurrency safety**: under Postgres's default Read Committed isolation, two concurrent requests could both read the same "not full yet" capacity sum before either commits, and both succeed. `createBookingHold` and `claimOrder` (the payment step) both guard against this with `tx.$queryRaw`SELECT id FROM listings WHERE id = ${id} FOR UPDATE`` on the `Listing` row before reading/writing — a second concurrent attempt on the same listing blocks until the first transaction commits or rolls back, so it always re-reads an up-to-date sum. Scoped to one row per listing, so unrelated listings never contend. `claimOrder` re-locks and re-checks expiry again at payment time (not just at hold-creation time), since a hold expiring at the exact instant another transaction is deciding whether it still counts is a real, if narrow, race otherwise.

This was verified, not just reasoned through: a throwaway script (reimplementing the same lock-then-check-then-create shape, since `createBookingHold` itself requires a real Next.js request and can't run from a bare script — `auth()` needs `next/headers`) fired two concurrent hold attempts at a capacity-1 listing with an artificially widened race window. Without the lock, both succeeded (confirmed double-booking). With it, exactly one did.

**Expiry is lazy** — a hold simply stops being counted once `expiresAt` passes (every capacity query filters on it); nothing actively deletes it for correctness, only for table housekeeping, which isn't built. This was the schema's own documented intent already (see `BookingHold`'s comment in `schema.prisma`), just not wired up until now. `Venue.holdDurationMinutes` defaults to 5 (not the originally-seeded 10) to keep manual testing fast.

**Availability math accounts for holds, not just confirmed bookings** — `getSpotsRemaining`/`hasAvailableSlotOnDate` in `lib/availability.ts` subtract active (non-expired) `BookingHold` quantities too, so "spots left" shown to other browsers stays accurate while someone else is mid-checkout.

**The pickers themselves are occupancy-aware for every mechanic now, not just `fixed_session`.** `FixedSessionPicker` always had this (`getSpotsRemaining`, above), but `TimeRangePicker`/`DateRangePicker` originally had zero knowledge of existing Bookings/BookingHolds — a held or already-booked court slot, or an already-booked campsite date, would still render as selectable to a different browser/account, only to be rejected after a round-trip to "Book Now." Closed by extending the same "fetch real occupancy once at page load, pass it down fully resolved" pattern to both: `getOccupiedIntervals` (per-date occupied minute-ranges, for `time_range`) and `getFullyBookedDates` (per-date capacity-exhausted set, for `date_range`), both in `lib/availability.ts`, computed in `app/listings/[id]/page.tsx` and threaded through `SlotPicker` into the mechanic-specific picker. This was always a UI-affordance gap, not a live double-booking hole — every seeded exclusive-use listing has `capacity: 1`, and the server-side `FOR UPDATE` check (above) already rejected the second attempt at submit time regardless; the fix is that the picker now disables/excludes it up front instead of letting you reach "Book Now" first.

## Payments (Stripe, test mode - GitHub #37, #39-#44)

**The Payment Element on the site's own checkout page, not hosted Stripe Checkout** - a deliberate choice. A hosted Checkout Session must stay open for at least 30 minutes, far longer than the 5-minute hold, so a customer could pay on Stripe's page after their hold had expired and the slot had gone to someone else. Extending holds to 30 minutes was rejected as too long. Paying on our own page means the server checks the hold at the moment of payment.

**Authorize, then capture.** PaymentIntents use `capture_method: "manual"`: the card is only authorized in the browser, and the money is taken only after the server has secured the booking under the listing lock. A payment that arrives after the hold expired, a duplicate payment for the same order, or an amount that doesn't match is released (PaymentIntent cancelled) - **the customer is never charged for a booking they didn't get**, and there are no refunds to issue.

Flow (all in `lib/bookings.ts`, `CheckoutForm` drives it):
1. `<Elements>` in deferred mode (amount + currency, no PaymentIntent yet), card only (`allowedPaymentMethodTypes: ["card"]` - no Link, wallets or redirects).
2. Submit: `elements.submit()`, then `startHoldPayment` validates attendee + hold and creates the PaymentIntent. Attendee details and `orderId`/`userId` go in its metadata, so the webhook can finish the booking without the browser. A free order (total 0) skips Stripe and is confirmed directly.
3. `stripe.confirmPayment({ redirect: "if_required" })` authorizes the card (3-D Secure in Stripe's pop-up).
4. `confirmHoldPayment` re-fetches the PaymentIntent (never trusted from the client), checks it belongs to this user and order, and calls `completeOrderPayment`.
5. `completeOrderPayment`: `claimOrder` converts holds into `pending` bookings in one transaction; then capture outside the transaction (no network call under a row lock); then flip to `confirmed`. A failed capture marks the bookings `cancelled` (frees capacity; hidden from My Bookings). Still settling = stays `pending`; the confirmation page shows "Finishing your payment" and refreshes until the webhook confirms it.

**Webhook** (`app/api/stripe/webhook/route.ts`, signature-verified with `STRIPE_WEBHOOK_SECRET`): `payment_intent.amount_capturable_updated` and `payment_intent.succeeded` re-fetch the PaymentIntent and call the same `completeOrderPayment`. It's idempotent - the listing lock serialises the browser and the webhook, and capture uses an idempotency key - so whichever arrives first does the work. This covers a closed tab after authorization.

**`pending` finally means something**: a booking whose card is authorized but not yet captured. It still counts against capacity (every capacity query excludes only `cancelled`).

Other details: one platform currency, `PAYMENT_CURRENCY = "aud"` (`lib/stripe.ts` - listings have no currency of their own); `Booking.stripePaymentIntentId` (renamed from the never-used `stripeCheckoutSessionId` by migration `stripe_payment_intent`); the checkout form never swaps to the expired-hold screen while a payment is in flight, so the server's answer ("you haven't been charged") always reaches the customer. Env: `STRIPE_SECRET_KEY`, `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY`, `STRIPE_WEBHOOK_SECRET`. The card fields' text is 16px below `md` and 14px above (`checkoutAppearance`, the same rule as the site's `Input`): iPhones zoom the page into any focused input under 16px, and Stripe's iframe is out of reach of the site's CSS. The hold countdown has `suppressHydrationWarning` (server and browser render it a second apart). Packages pinned to stripe 23.0.0 (API version `2026-09-30.endive` - `payment_method_types` was removed, use `allowed_payment_method_types`), @stripe/stripe-js 10.1.0, @stripe/react-stripe-js 7.0.0.

**Known gap**: if the browser closes after authorization and no webhook is configured (e.g. local dev without the Stripe CLI), the booking isn't completed and the authorization lapses on its own after about 7 days - never captured, so never charged.

## MVP scope — explicitly cut, do not build unless asked

Reviews/ratings, real-time notifications, venue-owner/multi-role staff accounts, geolocation-based search (no coordinates exist), live (non-test) payments, an admin UI for platform data - activities, tags, cities - and for user roles (seed script only; venues and listings are managed in the venue dashboard), guest checkout for the booking flow (schema-ready, deliberately deferred), true indefinite recurring `AvailabilityOverride` (see "Booking availability design" above for why).

## Natural-language search (GitHub #77)

The header search box takes plain language ("tenis in sydny this weekend for free", "racket sports somewhere warm") and turns it into the **existing browse filters** - the search itself is always done by the browse page, so results match what the sidebar would show.

- **Flow:** `HeaderSearch` (Enter) -> `searchAction` (`app/search/actions.ts`, input parsed: query 1-200 chars, viewer's `today`) -> `interpretWithLlm` (`lib/llm.ts`) or, on any failure, `keywordInterpret` (`lib/search/keyword.ts`) -> `interpretationToParams` (`lib/search/interpretation.ts`) -> `router.push("/?...")`. The query stays in the URL as `q`; `SearchInterpretation` (browse page) shows removable "Showing results for ..." chips while `q` is present.
- **`lib/llm.ts` is the only file that talks to the LLM provider** (Anthropic SDK, model `claude-haiku-5-5`, key in `LLM_API_KEY` - deliberately provider-neutral name). Structured output via `messages.parse` + `zodOutputFormat`, thinking off, effort `low`, 8s timeout, 1 retry; returns `null` on any failure (no key, error, timeout, refusal, unparseable) so the caller falls back. Not `server-only` so the eval script can import it; the key has no `NEXT_PUBLIC_` prefix, so it can't reach the browser.
- **The schema is the guardrail:** built per call from the search vocabulary, tags and cities are enums of real database values, so the model can't invent a city. Booking type is **single-valued or null** (the browse category filter selects one type or all), set only when the query clearly asks for exactly one. Dates: the model only classifies `when` (today, tomorrow, this/next weekend, a weekday, a specific date); `resolveWhenToDateParam` does the calendar math in code, using the same Saturday/Sunday rule as the "This weekend" pill. Times of day are ignored (browse filters by day).
- **Vocabulary** (`getSearchVocabulary`, `lib/search/vocabulary.ts`): tags, cities (with region/country, for "somewhere warm"), and activity -> tag mappings, cached for an hour under the same cache tags as the browse lists - a search doesn't hit the database. **"Classes" is excluded from the tags** on purpose: several tags mean "any of these", so "tennis class" as Tennis + Classes would match every class; class intent goes through the booking type instead.
- **URL conventions:** tags are written lowercase (the tag tiles compare lowercase - capitalised tags filtered correctly but didn't highlight the tiles); `city` can now hold several comma-separated names (`lib/city-filter.ts`), with the city dropdowns showing a disabled "Multiple cities" entry while several are active.
- **Evaluation:** `pnpm exec tsx -r dotenv/config scripts/search-eval.ts` - 26 queries (typos, synonyms, booking-type rules, dates, prices, a prompt-injection attempt, nonsense) with expected filters; costs a fraction of a cent. Last run: 26/26, median ~1.3s per call. Re-run after any change to `lib/llm.ts` or `lib/search/`.
- **Why query understanding, not embeddings:** the catalogue is structured (sport, city, schedule, price), and searching it is about intent - dates, price, "somewhere warm" - which similarity search can't express, and typos break date parsers. Embeddings remain a possible later ranking step within filtered results.
- **No rate limiting on search** (explicit decision): each search costs a fraction of a cent; the spend limit in the provider console is the backstop.

## Security decisions and known gaps

From a security audit (fixes applied; deferred items are deliberate):
- **Slot-set rules are server-enforced** (`lib/slot-rules.ts`, called from `loadAndValidateListing`): exactly one slot for `time_range`/`fixed_session`/accommodation; a pass gets one-day slots, no repeats, count within `minDurationDays..maxDurationDays`. Before this, the server trusted the picker's slot count (a crafted request could hold up to 100 court slots under one order).
- **Google sign-in links to an existing password account with the same email** (`allowDangerousEmailAccountLinking`), and `events.linkAccount` then clears that user's `passwordHash`. This lets the verified owner reclaim an address someone pre-registered (signup has no email verification). Trade-off: a user who links Google loses password login until a reset flow exists.
- **`authorize()` runs bcrypt against a dummy hash when no user exists**, so login timing doesn't reveal registered emails.
- **Row-level security is enabled (no policies) on every table** (migration `enable_rls`), as a backstop behind Supabase's public API. The app connects as `postgres` (owner, `BYPASSRLS`) and is unaffected. **Any new table needs `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` in its migration.**
- **`server-only`** guards `lib/availability.ts`, `lib/browse-tags.ts`, `lib/browse-cities.ts`, `lib/bookings.ts`, `lib/auth-guards.ts`. Not `lib/prisma.ts`: `prisma/seed.ts` and `scripts/test-connection.ts` import it from bare scripts.
- **Browse URL params are parsed with fallbacks** (`lib/validation/browse.ts`), both server-side (`ListingSection`) and client-side (`BrowseSidebar`, `QuickFilters`). A bare `Number("abc")` there once sent the price slider into an infinite render loop (`NaN !== NaN`), crashing the page from any link.
- **Length caps**: names 100 chars, emails 254, passwords 72 UTF-8 bytes (bcrypt's limit; longer inputs would otherwise be silently truncated).
- `/test-connection` (a Phase 0 diagnostics page, public and printing raw DB errors) was removed.

Known gaps, deliberately deferred:
- **No rate limiting and no email verification.** Scripted signups can still each hold one slot for 5 minutes at a time; signup also reveals whether an email is registered (unavoidable without verification). For the README's "intentionally cut" section.
- **Role changes only take effect on next sign-in** (role lives in the JWT). Nothing changes roles yet; when an admin UI does, have the `jwt` callback re-read the role periodically.

**`date_range` dates are calendar days, never instants** (fixed bug): `date_range` slots are stored as UTC midnight of the picked day. `isRequestedSlotValid` reads their day with `startOfUTCDay`, and `formatBookingTime` (which now takes the listing's `bookingMechanic`/`isAccommodation`) formats them in UTC. Both used to go through the venue's timezone, which at venues behind UTC (e.g. America/New_York, where UTC midnight is the previous evening) rejected "today" as unbookable and displayed every date a day early. Courts and classes still store and display real instants in the venue's timezone. Display rule: a stay shows check-in to check-out; a pass shows its last booked day (the stored exclusive end minus one), so one pass day reads as a single date.

**Same-day cut-off for `date_range` listings** - booking a venue that has already closed must not be possible. No new column: it reuses `Listing.operatingHoursEnd` (opening hours for a pass, the check-in deadline for a campsite). `isSameDayBookingClosed` (`lib/time-of-day.ts`) closes "today" once the venue's local time reaches closing time minus `SAME_DAY_CUTOFF_BUFFER_MINUTES` (60), and **fails closed**: a `date_range` listing with no `operatingHoursEnd` never allows same-day booking. Applied inside `getBookableDates`, so the calendar, browse date filter and the server's check of a submitted booking all follow it (a page loaded before the cut-off and submitted after it is rejected server-side). Every seeded `date_range` listing has hours (gym passes 06:00-22:00, campsites 08:00-20:00). Venues closing after midnight aren't supported (none exist). Courts and classes don't use it - they already reject past start times and must end by closing.

## Prisma 7 gotchas (important — Claude Code's training data may predate these and give outdated advice)

This project hit several real breaking changes going from "how Prisma tutorials generally describe it" to actual Prisma 7 behavior. Do not follow older Prisma patterns without checking current docs first:

- `schema.prisma`'s `datasource` block no longer takes `url` or `directUrl` at all (both removed in v7). Connection URLs live exclusively in `prisma.config.ts`, under `datasource: { url: env(...) }`. `directUrl` has no v7 replacement in `prisma.config.ts` either — only one URL for the CLI, and it should be the direct/non-pooled one (migrations need session-level features pooling doesn't support).
- The `generator client` block requires an explicit `output` path (no default location anymore), and uses `provider = "prisma-client"` (not the older `"prisma-client-js"`).
- The running app's `PrismaClient` must be constructed with an explicit driver `adapter` (this project uses `@prisma/adapter-pg` + `pg`, wrapping a connection pool) — see `lib/prisma.ts`.
- **Seeding is no longer automatic.** `prisma migrate dev` / `prisma migrate reset` do NOT run the seed script anymore, even with `migrations.seed` correctly configured in `prisma.config.ts`. You must explicitly run `prisma db seed` as a separate command after migrating.
- Connecting to Supabase via `pg`/`@prisma/adapter-pg` throws `self-signed certificate in certificate chain` by default — fix is appending `&uselibpqcompat=true` to the pooled connection string (`POSTGRES_PRISMA_URL`).
- Vercel's Supabase integration provides `POSTGRES_PRISMA_URL` (pooled, port 6543, use for the app's runtime `PrismaClient`) and `POSTGRES_URL_NON_POOLING` (direct, port 5432, use for `prisma.config.ts`'s CLI connection / migrations). Don't confuse the two.
- Deploying to Vercel requires a `"postinstall": "prisma generate"` script in `package.json` — the `generated/prisma` client output folder is (correctly) gitignored, so nothing generates it automatically on a fresh Vercel checkout otherwise.
- pnpm specifically (not npm) blocks Prisma's install scripts by default (`ERR_PNPM_IGNORED_BUILDS`) — fix with `pnpm approve-builds prisma @prisma/engines` then `pnpm install`.
- A Prisma 8 release candidate exists but is pre-release — deliberately staying on 7.9.1 for the rest of this build.
- `prisma migrate reset` run by Claude Code specifically requires the user's explicit, freshly-given consent passed via the `PRISMA_USER_CONSENT_FOR_DANGEROUS_AI_ACTION` env var (Prisma's own agent-safety check) — a prior message's consent earlier in a conversation does not carry forward automatically.

## Other dev-tooling gotchas

- **A space after a JSX element or `{value}` can vanish** when the text after it wraps onto further lines (`<Link>Contact</Link> page. Use…` over two lines rendered "Contactpage."; `{venueName} is sample…` rendered "Clubis"). Single-line text is fine. Put an explicit `{" "}` after the element, or build the sentence as one template string - as the codebase already does (`I agree to {venueName}&apos;s{" "}`).
- **The dev server can keep serving a stale `app/globals.css`** - even after a restart. A change to a CSS variable (`--muted-foreground`) never reached the browser until the dev cache was cleared: stop `next dev`, `rm -rf .next/dev`, start it again. Check what's actually served (fetch the page's CSS chunk and grep for the variable) before concluding a style change "didn't work".

- `import "server-only"` at the top of a module only does anything inside Next's own bundler (dev server / `next build`) — running a file that imports it through a bare script (`tsx`, plain `node`) throws unconditionally, since the real npm package has no way to distinguish "server context" outside Next's own build pipeline. Install the real `server-only` package (as Next's own docs suggest) if you need such a file to also be runnable/testable outside Next — but expect to still need the import temporarily removed for a one-off script, since the package always throws when actually executed outside Next's bundler.
- `auth()` (from `auth.ts`) depends on `next/headers`, which only works inside a real Next.js request. It cannot be exercised via a standalone script under any circumstances — there is no bare-script workaround, this has to be tested through the running app.

## Conventions

Ticket IDs follow `phase.subtask` (e.g. `5.4`) and are used as human-readable references in commit messages and on the GitHub Projects board. **Important:** GitHub Issues for this project were created manually, one by one, directly on GitHub — the `create_github_tickets.sh` bulk-creation script was written but never actually run, because it got fiddly to work with. This means GitHub's own auto-assigned issue numbers do **not** match the phase.subtask ticket numbering. If a commit needs to actually link to a GitHub issue (e.g. `closes #N`), `N` must be looked up as that ticket's real GitHub issue number — never assume it equals the phase.subtask number (e.g. ticket `5.3` might actually be GitHub issue `#17`). The phase.subtask number should **not** appear in the commit message text, only the task name, GitHub's #N number to be entered manually on commit. Work happens on a `dev` branch; `main` is production and auto-deploys via Vercel on merge.

## Coding standards

All code written for this project — by Claude or otherwise — must be commented to a professional, production standard: explain intent and non-obvious reasoning (why a decision was made, what edge case is being handled, why one approach was chosen over another), not restate what the code already visibly does. Write comments assuming a new developer with zero prior context on this project needs to read them and pick up the work. Avoid comment noise (e.g. `// create a user` above a line that obviously creates a user) — every comment should earn its place. This is the standard already set in `prisma/seed.ts` and should be matched in every file going forward, to keep the codebase maintainable and easy for any engineer joining the project to pick up.

**Prefer industry-standard, maintainable patterns over the shortest path, even when that costs more upfront complexity.** Concretely: a check that matters for security or correctness (auth, authorization, input validation) should be structural — enforced by the type system or a shared wrapper a function can't be called without going through — rather than a convention every new function has to remember to repeat. Example already in this codebase: `lib/auth-guards.ts`'s `withAuth`/`withPermission` wrap Data Access Layer functions (see `lib/bookings.ts`) so a function literally cannot run without a session/role check having already happened, instead of each function starting with its own `if (!session) ...`. This is a deliberate exception to "prefer the simpler, shippable option" elsewhere in this file — scope discipline is about not building unneeded features, not about cutting corners on how the features that do exist are built.
